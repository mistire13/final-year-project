# Subscription payment provider research

Research date: 7 November 2026. Sources are the public Veritas documentation and its linked upstream verifier repository. No live receipts, Veritas credentials, customer information or actual transfer were used. This is a field and risk inventory, not proof that the current hosted API returns every listed field for every institution.

## Veritas contract

- [Single-payment verification](https://veritas.et/docs/verification) documents provider-specific routes and inputs. `/verify` can detect most providers; M-Pesa requires its dedicated route. CBE legacy FT references need an account suffix; Bank of Abyssinia requires a five-digit suffix; CBE Birr requires an Ethiopian phone number.
- The same documentation says that HTTP 200 can include a provider failure and that receipt response envelopes differ: CBE and M-Pesa are commonly top-level, Telebirr is nested under `data`, and Abyssinia can have an additional envelope. Do not treat HTTP 200 or a `success` flag alone as proof of a completed payment. Requests consume verification credits even when lookups fail.
- [Provider identifiers](https://veritas.et/docs/reference/providers) list CBE legacy FT references and new tokens/URLs, Telebirr, CBE Birr, Dashen, Abyssinia and M-Pesa. New CBE receipt tokens and URLs are case-sensitive; preserve them exactly. Dashen references can be numeric-only. Do not strip URL characters, fold case for new CBE tokens, or equate aliases unless independently verified as the same transaction.
- The [linked upstream repository](https://github.com/Vixen878/verifier-api) describes itself as unofficial and not affiliated with the underlying banks or telecom operators. Its response structures and availability can change; the README's illustrated values are synthetic examples, not verified live receipts.
- The [upstream Dashen example](https://github.com/Vixen878/verifier-api#-dashen-bank-verification) uses fields such as `receiverName`, `transactionReference`, `transactionDate` and `transactionAmount`. That example does not establish an explicit currency, completion status, or receiving account. Treat missing confirmation as inconclusive, not as implied success or ETB.
- The upstream [Telebirr receipt parser](https://github.com/Vixen878/verifier-api/blob/main/verify.php) emits nested fields including `creditedPartyName`, `creditedPartyAccountNo`, `transactionStatus`, `receiptNo`, `paymentDate` and `settledAmount`. The parser can return missing or empty fields; the observed source is not a guarantee that all hosted responses have identical fields. The receiver for bank transfers can differ from the bank label. Compare the settled payment amount rather than the payer's fee-inclusive total when the provider supplies both.
- [Getting started](https://veritas.et/docs/getting-started) requires a server-side API key sent in the `x-api-key` header. Never send the secret to the browser or log it. Store only the minimum evidence needed for reconciliation and protect payment metadata.

## Safe handling for Ankelba

1. Snapshot the super administrator's receiver name, receiving account, amount and currency into each payment intent before the customer pays.
2. Normalize response shape using explicit provider adapters and approved test fixtures. An automated acceptance needs independently established completion, exact amount/currency, a matching receiver name, a sufficiently identified receiving account where applicable, and a trusted transaction identity. Normalize the name only for Unicode form, casing and insignificant whitespace; do not use fuzzy-name acceptance.
3. A missing, masked, contradictory, or otherwise ambiguous field must remain pending for independent operator review. A screenshot supplies only a candidate reference. The operator's written reason is not itself proof; require independent verification of the actual amount, destination and transaction.
4. Claim a confirmed provider transaction identity atomically in a durable uniqueness ledger, across onboarding and renewal. Unverified references must remain correctable and must not permanently reserve another payer's receipt. Preserve confirmed claims through refunds and cancellations. Never automatically merge or release ambiguous historical aliases.
5. Integration approval requires authorized sanitized real or provider-approved test receipts for each supported provider, including success, not found, invalid, masked receiver, mismatched account/name/amount and failure responses. No such receipts or live verification were available during this research. Until mappings are verified, uncertain cases require manual handling.

## Hosted checkout alternative

[Veritas payment-link documentation](https://veritas.et/docs/commerce/payment-links) states that checkout confirmation checks amount, payout destination and duplicate references. It requires the corresponding paid workspace capability, and its published description does not establish that it also matches Ankelba's separately configured receiver name. Integrating hosted checkout would be a separate product and architecture decision; it is not a substitute for proving the required receiver-name check.
