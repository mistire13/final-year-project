# Platform subscriptions

The platform subscription is separate from daycare tuition and parent store payments. New applicants select Standard or Premium and a monthly, six-month or annual period, pay, submit their application and wait for platform approval. The first paid period begins on approval. There is no free trial. Package terms and the receiving account are saved with each payment session.

Subscription payments support **Telebirr**, **Commercial Bank of Ethiopia (CBE)** and **Bank of Abyssinia**. In Subscription Billing → Receiving accounts, the super administrator enables each method separately with its account-holder name and receiving details: an Ethiopian phone number for Telebirr, or a full bank account number for CBE/Abyssinia. Accounts start disabled until explicitly configured; legacy example details are never automatically activated. Signup and renewal require an enabled payment method before creating a session. The chosen method and receiving details remain fixed for that session even if settings later change.

Telebirr accepts a transaction reference and normalizes Ethiopian phone formats for exact account matching. CBE accepts only the complete HTTPS receipt link copied from CBE. Signup and renewal display one URL field, without a suffix field or screenshot extraction. The backend validates the CBE host and receipt identifier. When a legacy link embeds an FT reference and eight-digit suffix, the backend extracts both; modern opaque receipt URLs are passed intact to Veritas. Bare CBE references, incomplete links and separately submitted CBE suffixes are rejected with guidance to paste the complete link. Bank of Abyssinia requires the reference and a five-digit account suffix. These suffixes are receipt-verification details and must not be assumed to be the receiving account's last digits. CBE tokens and URLs retain their case. Only known CBE receipt hosts are accepted for links; arbitrary URLs and credential-bearing URLs are rejected.

Historical Telebirr and other payment records remain intact. They are not silently reassigned to a bank. Previously submitted payments retain the operator review flow; an operator may also review an old pending session using independently verified reference, evidence, reason and amount/receiver confirmation. Confirmed references still enter the permanent reuse ledger. Customers who already paid should contact the platform team instead of paying again.

Public registration starts at `/pricing`. Homepage Register actions open this full page, where customers compare Standard and Premium first, then compare three detailed period cards. Payment and application forms continue inline. The page uses the landing-page brand and animated atmosphere, with motion controls and responsive layouts. Unconfigured periods are unavailable. Longer-term savings are shown only when the configured total is genuinely lower than monthly billing over the same period, with that comparison explicitly labeled.

Accepted payment terms remain fixed during recovery. Valid emailed recovery credentials are saved in session storage immediately after the URL is scrubbed and before the status request. Creating a payment session temporarily locks plan changes; a confirmed explicit restart clears the old recovery and returns to the current catalog. Application submission blocks link/history navigation while the request is pending and warns on reload or window close. Inputs and confirmed payment remain available after submission errors; passwords are never saved as a browser draft.

Platform operators configure the offered prices and capacities before accepting payments. A receipt screenshot can be scanned on the server with Tesseract; its text is only a suggestion for a reference number. The applicant can enter or correct that reference. Veritas is called from the backend, and inconclusive transactions remain pending for an operator to verify independently and record an audited decision. A confirmed payment does not itself approve an application.

For automatic confirmation, the verified transaction must establish a successful status and match the captured amount, currency, receiver name, receiving account, reference, and date. The receiver name and account are captured from the platform operator's settings when the payment session starts. Provider responses that are incomplete, masked or mismatched remain pending; the operator must independently verify the actual transfer, amount and destination before approving. Confirmed transaction references and verified aliases are recorded in a durable ledger and cannot be reused across customers, payment providers, registrations, renewals, cancellations or refunds. Unverified attempts are recorded separately and may be corrected without reserving the reference.

After expiration the account may still read records and use attendance, health/incident recording, biometric verification and pickup. Other operational changes require a verified renewal. Billing, authentication and platform governance remain available. The daycare administrator sees its subscription and a notice beginning five days before expiry.

## Deployment prerequisites

- Back up the database, then complete database migrations and runtime-role setup before starting the updated backend. Migration 047 preserves historical confirmed references and refuses conflicting evidence; investigate conflicts rather than discard or overwrite them. Migration 048 adds separate bank-account settings and widens reference storage for CBE receipt links without changing old payment snapshots. Prices must be set for each package/period, and at least one receiving account must be configured and enabled before initiating payments.
- Set `VERITAS_API_KEY` server-side and confirm the supported providers and their returned amount, currency, recipient, date and reference fields against actual test transactions. An incomplete response is not marked paid. Configure `VERITAS_API_URL` only for an explicitly trusted service.
- Install Tesseract OCR with English language data on the backend host. Set `SUBSCRIPTION_OCR_COMMAND` to its executable if it is not on PATH. Customers can enter references manually if scanning is unavailable.
- Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, and the public `FRONTEND_URL`; then set `SUBSCRIPTION_REMINDERS_ENABLED=true`. A worker checks for reminders every 15 minutes, retries failed sends and deduplicates each administrator and paid period. SMTP is an external service and delivery must be verified separately. A crash after SMTP accepts a message can cause a retry because email cannot guarantee exactly-once delivery.
- Establish operator procedures for independently verifying pending receipts, resolving rejected/abandoned paid applications, and restoring an applicant's interrupted payment session. Do not mark refunds or provider verification as completed without evidence.

Existing pre-subscription daycare records with no accepted terms or paid-through date are not assigned an invented debt or restricted automatically. Test data cleanup must target only confirmed test records, after a backup and while preserving the platform operator.

On 6 November 2026, the local `ankelba_dev` test data was cleaned after a backup and a successful rehearsal against a restored disposable copy. The cleanup preserved the global operator, platform accounts, roles, package catalog, payment settings, sessions and MFA factors. The backup is stored locally under `tmp/subscription-backups/` and is excluded from Git.

## Temporary local verification testing

For the user's local test on 8 November 2026, `backend/.env` enables `SUBSCRIPTION_NAME_AMOUNT_TEST_MODE=true`. It is honored only with `NODE_ENV=development`; production always uses strict matching. In this diagnostic mode a trusted successful provider result must match the exact configured receiver name (case/spacing normalized) and exact payable amount. Account number, currency, reference binding and transaction date are not approval requirements in this mode. Explicit failed/pending statuses and failed provider envelopes still cannot approve a payment. Valid receipt input, bank/session binding and permanent duplicate-reference protection remain enforced. CBE link identifiers and authoritative transaction references are both claimed. Verification metadata records `name_amount_test`.

Set `SUBSCRIPTION_NAME_AMOUNT_TEST_MODE=false` and restart the backend to restore the full matching rules locally. This mode is for controlled testing, not accepting real subscriptions.

The same local test reset cleared four unconfirmed session references and 16 attempts after a verified database backup. There were no confirmed reference claims, linked paid applications or recorded renewals. Prices, receiving settings and the seven existing payment sessions were retained. At the user's subsequent request, all seven pending sessions and two later attempts were deleted after another verified backup; there were no pending daycare applications. Saved browser sessions that no longer exist offer an explicit “Return to pricing” action, with guidance to contact support if money was already transferred.

The maintenance command `node scripts/reset-subscription-test-references.cjs` performs read-only checks by default; `--apply` creates a fresh private backup and resets only an unlinked local test dataset. Add `--remove-pending` to delete an exclusively pending test dataset instead of retaining its sessions. It refuses confirmed/linked financial history and non-pending records for the deletion mode.
